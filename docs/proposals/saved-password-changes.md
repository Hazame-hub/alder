# Saved plans that carry password changes, without the password

**Status: proposed (2026-11-01). No code until it is accepted.**

`alder plan --out` saves a reviewed plan, and `alder apply --plan` applies
exactly that plan later, refused if the directory moved in the meantime.
Since 1.42 that covers adds, modifications, deletions, renames and moves.
The one change it still refuses is a password change. This proposal lets a
saved plan say "set the password of *this* entry" without ever holding the
password. The secret is supplied when the plan is applied.

---

## The problem

A team that reviews directory changes and applies them from CI cannot put a
password change through that loop:

- `alder plan --out` stops with `plan_not_saved` ("set_password of … is not
  a change a saved plan holds"), so the change goes through `alder apply`,
  with nobody's review attached.
- The obvious fix, saving the password in the plan, is wrong. The plan is
  the file people read, sign, attach to a pull request and keep. Hard rule 6
  says a password is never written to a file, and a signed plan is a file
  that lives forever.

What a reviewer can usefully approve is the **intent**: this entry, and no
other, gets a new password. The new password itself is best chosen when the
change is applied, for example generated by the job and handed to its owner
once, or taken from a secret store.

The cases this serves:

- rotating a service account's password from a scheduled, reviewed job,
  with the new value going straight from a secret manager to the directory;
- a helpdesk tool in front of Alder that has an operator approve a reset,
  then generates a temporary password at apply time.

## What exists today

- **`setpassword`** (RFC 3062) is a `ChangeRequest` type with a write-only
  `newPassword`. It is never echoed, never rendered as LDIF or Ansible, and
  never logged (`internal/directory/change.go`, `internal/api/convert.go`).
- **It plans:** `ActionSetPassword` when the entry exists, and
  `entry_missing` otherwise (`internal/plan/plan.go`). It is never
  `unchanged`, because a directory cannot be asked whether a password is
  already the one being set.
- **The baseline binds the secret** with a keyed, session-scoped MAC
  (`secretDigest`, `internal/plan/baseline.go`). So applying a different
  password than the one planned is refused, and a token cannot be used to
  test guesses offline.
- **Recovery already says** "password not captured" for this step
  (`ReasonPasswordNotCaptured`).
- **`apply --plan` plans again before writing**, in its own session, and
  checks every saved expectation. Saved renames bind the entry by identity
  (`entryUUID`, else `nsUniqueId`) since 1.42.
- **Validation refuses an empty `newPassword`** everywhere
  (`ChangeRecord.Validate`, `changeRecordFrom`).

## The proposal

### 1. The saved change holds no value

`alder plan --out` saves a `setpassword` change as its type and DN, plus an
**identity expectation** made exactly as a saved rename's is: `entryUUID`,
else `nsUniqueId`, with the values the entry returned. A deleted and
re-created entry with the same DN makes the plan stale. `newPassword` is
never written to the file. The reader refuses a file in which a password
change carries one.

The input is `--changes` (LDIF has no form for this change) with
`"type": "setpassword"` and **no** `newPassword`. If the input does carry a
value, `plan --out` refuses it: the point is that the value never passes
through the review.

### 2. `POST /plan` accepts a password change without a value

This is the one API change, and it is an addition. At plan time,
`newPassword` may be absent on a `setpassword` change. The plan then
reports the item as `set_password` with a new field,
`passwordSuppliedAtApply: true`, and its operation is bound without a
secret. `POST /changes/apply` and `POST /changeset/apply` still refuse a
password change without a value (`a password change requires
newPassword`). An unsaved plan never reaches apply without one, because the
web interface always sends the value it asked for.

No baseline is weakened by this. `apply --plan` plans again **with** the
password before writing, in the session that applies, so the token it
applies with binds the real secret as today.

### 3. `alder apply --plan` takes the secret, never from the plan

One password per password change, in the order the plan lists them, from
exactly one of:

1. `--new-password-file PATH`: one password per line, without line endings.
   `/dev/fd/N` works, so a caller can pass the secrets on a file
   descriptor of their own and leave stdin for `--bind-password-stdin`.
2. `--new-password-stdin`: the same, from standard input. It is refused
   with `--bind-password-stdin` or a plan read from `-`, as standard input
   is read once.
3. The terminal: asked for each entry by DN, with echo off, twice to
   confirm. Only at a terminal.

**Never from the environment.** The other credentials do read the
environment (`ALDER_BIND_PASSWORD`), but a variable is inherited by every
child process. A new user password has no reason to be there.

The count must match: fewer or more passwords than password changes is
exit 2, before anything is read from the directory. An empty line is
refused, as an empty bind password is. With `--yes` and no file and no
stdin given, apply fails at once (exit 7), as a missing bind password does.

### 4. What is shown, signed and kept

- **The plan file and its signature** cover the type, the DN and the
  identity expectation. Signing a plan with a password change therefore
  signs "this entry gets a new password", which is what an approver can
  judge.
- **The human output and `--json`** say `set_password` and that the value
  was supplied at apply. They never include the value or its length.
- **The recovery bundle** records the step as "password not captured", as
  it already does.
- **The web saved-plan loader** refuses a plan with a password change and
  names the command that applies it. The browser has no secret file to
  read, and asking for a password there would be a new page of its own.

### 5. Conformance

On both servers:

- save a password change, then apply it with `--new-password-file` and
  bind as the entry with the new password;
- delete and re-create the entry, and see the apply refused as stale with
  nothing written;
- give one password too many, and see exit 2 with nothing written;
- check that the plan file, the `--json` output and the server log hold
  no line containing the password.

## Not in this proposal

- **Generating passwords.** That is the caller's policy (length, alphabet,
  delivery). Alder sets the value it is given.
- **Forcing a change at next login.** That is the directory's password
  policy (`pwdMustChange`, `passwordMustChange`). `GET /policy` already
  reports it per entry.
- **The web interface applying a saved password change.**

## What it changes, when built

- `api/openapi.yaml`: `newPassword` becomes optional on `POST /plan` for
  `setpassword`, and `PlanItem.passwordSuppliedAtApply` is added. Only
  additions; COMPATIBILITY.md gets a 1.43 section.
- CLI: `apply --plan` gains `--new-password-file` and
  `--new-password-stdin`, and `plan --out` saves a password change.
- The saved-plan format stays `alder-plan` version 1. An older release
  refuses a file holding a password change, as it does today.
- A DECISIONS entry, and SIGNING.md's "signing a saved plan" section names
  what a signature on a password change covers.

## Open questions for review

1. **Order and count** (recommended), or **lines keyed by DN** in the
   password file? Keyed lines cannot be applied to the wrong entry, but a
   DN can hold any character, and a file format with escaping is one more
   thing to get wrong. Order plus count, with the plan listing the DNs in
   that order, is what the terminal prompt does too.
2. **Ask twice at the terminal** (recommended), or once?
3. **Refuse a value in the `plan --out` input** (recommended), or ignore
   it with a warning?
