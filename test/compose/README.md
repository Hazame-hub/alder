# The conformance harness

Two directory servers, both with TLS from the same test CA, both holding
byte-identical data under `dc=alder,dc=test`. Everything Alder claims to do on
"OpenLDAP and 389 DS" is decided here.

```sh
task compose:up      # build, start, seed
task compose:logs    # follow
task compose:down    # stop, keep the test CA
task compose:reset   # stop and discard the test CA too

task compose:bulk -- 100000   # a different harness: the above, plus filler
```

`compose-up` is idempotent and safe to re-run. There are no data volumes, so
`down` then `up` gives a clean directory and re-seeds it. The only thing that
survives is `certs/`, because reissuing certificates on every start would mean
no client could ever pin the CA.

## Endpoints

| | OpenLDAP | 389 DS |
|---|---|---|
| LDAP | `ldap://localhost:10389` | `ldap://localhost:11389` |
| LDAPS | `ldaps://localhost:10636` | `ldaps://localhost:11636` |
| Inside the compose network | `openldap:389` / `openldap:636` | `ds389:3389` / `ds389:3636` |
| Bind DN | `cn=admin,dc=alder,dc=test` | `cn=Directory Manager` |
| Password | `alder-admin` | `alder-directory-manager` |
| Config bind DN | `cn=admin,cn=config` / `alder-config` | same Directory Manager |

The CA to verify against is `test/compose/certs/ca.crt`. Both server
certificates carry `DNS:<service>`, `DNS:localhost` and `IP:127.0.0.1`, so
verification succeeds from inside the network and from the host. **No client in
this repository is allowed to skip certificate verification**; if a test needs
to, the harness is wrong, not the test.

These credentials are test fixtures. They are in the repository on purpose and
they secure nothing.

There is also an unprivileged account for tests that must not run as root:
`cn=svc-alder,ou=services,dc=alder,dc=test` with password `alder-service`.

## What is seeded

320 entries per server, identical on both.

| File | Contents |
|---|---|
| `seed/00-base.ldif` | The suffix, three OUs, one service account. Hand-written. |
| `seed/10-users.ldif` | 300 users across 6 teams, with a custom auxiliary class, some on-call flags, some folded long values. |
| `seed/20-groups.ldif` | Six team `groupOfNames`, plus `cn=infrastructure` and `cn=everyone`, which nest two levels deep. |
| `seed/30-edge-cases.ldif` | Non-ASCII and CJK RDNs, an RDN with an escaped comma, values needing base64, binary data. |

Everything but `00-base.ldif` is generated by `test/compose/seed/gen` and
committed. Change the generator, run `task seed`, commit the diff. CI checks
that the committed output matches the generator.

## Bulk mode, for scale work

```sh
task compose:bulk -- 100000    # rebuild the harness with 100,000 extra entries
task compose:down              # ... and afterwards, to get rid of them
task compose:up                # back to the plain 320-entry harness
```

Opt-in, and nothing about the default harness changes. `task compose:up` still
produces exactly the 320 seeded entries above, which is what the conformance
suite asserts; bulk mode is a **separate harness state** that `compose:bulk`
builds from scratch and `compose:down` throws away.

What it adds is however many entries you asked for, under
`ou=bulk,dc=alder,dc=test`, named `uid=bulk0000001` and up. They are filler, not
fixtures: they exist to make the directory big, they carry `uid` and `alderTeam`
because those are the two the scale work measures, and **no test may depend on
them**. The seeded entries stay where they were and stay exactly what they were,
so a search that finds `uid=user0042` finds the entry it always did.

### Why it is not just more seed data

Loading six figures of entries over LDAP turns scale work into an afternoon of
waiting. Measured on this harness, same generated file, same machine:

| Entries | over LDAP, `ldapadd` | offline | |
|---|---|---|---|
| OpenLDAP, 15,000 | 125 s | **3 s** | `slapadd` |
| 389 DS, 15,000 | 61 s | **5 s** | import task |
| OpenLDAP, 100,000 | 863 s | **45 s** | `slapadd` |
| 389 DS, 100,000 | 790 s | **58 s** | import task |

Both servers can write to their database files directly instead of doing a
hundred thousand LDAP round trips, and bulk mode uses that on both. The whole of
`task compose:bulk -- 100000` — generate the 40 MB file, rebuild both containers,
load them, seed the 320 fixtures over LDAP as usual, and count what arrived on
each — takes **299 s** from an empty harness. Loading the same data over LDAP is
1,653 s before anything else happens.

### How each server takes it

They take it very differently, which is the usual state of affairs here.

**OpenLDAP** gets `slapadd`, which needs slapd stopped. In a container the only
moment slapd is stopped is before it starts, so the load happens in
`openldap/entrypoint.sh`, guarded by `ALDER_BULK_LDIF`. That variable is empty
unless `compose:bulk` set it, which is why `compose:bulk` has to recreate the
container rather than add to a running one. The entrypoint also raises the mdb
map size for the load, because 100,000 entries fill 230 MB of `slapd.conf`'s
256 MB map and the next size up would fail halfway with `MDB_MAP_FULL`. The
raised map is a sparse file: 8 GB apparent, 230 MB on disk.

**389 DS** has no offline *append*. `dsctl ldif2db` and the online import task
both replace the entire contents of the backend they are given, so importing the
filler into `userRoot` would delete the seeded fixtures. The filler therefore
gets a backend of its own — `ou=bulk,dc=alder,dc=test`, chained under the seeded
suffix by `nsslapd-parent-suffix`, in `ds389/bulk-backend.ldif`. A subtree search
at `dc=alder,dc=test` descends into it through the mapping tree, so a client sees
one tree; the import only ever replaces the throwaway half. `scripts/bulk.sh`
starts it by adding an entry under `cn=import,cn=tasks,cn=config` and waiting for
`nsTaskExitCode`, which is what `dsconf` does anyway and keeps the harness's
habit of configuring 389 DS over LDAP.

Both loads end in `scripts/bulk.sh` counting what actually arrived on each
server and refusing to report success unless the two agree.

### The generated file

`test/compose/seed/gen -bulk N` writes `test/compose/bulk/bulk.ldif`. It is
gitignored, and it should stay that way: a hundred thousand entries is about
40 MB, which is not something every clone of this repository should carry for a
measurement taken a few times a year. `task compose:bulk` regenerates it, so the
count on the command line is always the count in the directory.

The generator writes fixtures or filler, never both in one run. `task seed` is
the fixtures — deterministic, committed, checked by CI. `-bulk` is the filler,
and its header says so on the first line of the file.

## Where the two servers actually differ

The harness exists to find these. Each one is a place Alder must branch on a
capability, never on a vendor name.

| | OpenLDAP | 389 DS |
|---|---|---|
| Subschema entry | `cn=subschema` | `cn=schema` |
| Custom schema install | compiled into `cn=config` at image build | LDAP modify of `cn=schema` |
| Creating the suffix | a `database mdb` stanza in `slapd.conf` | add a backend entry **and** a mapping tree entry to `cn=config`; the container's `DS_SUFFIX_DN` alone leaves the server with no `namingContexts` at all |
| `userPassword` on write | stored as given | rehashed to `{PBKDF2-SHA512}` |
| Entry identity | `entryUUID`, `entryCSN` | `nsUniqueId`, `modifyTimestamp` |
| Loading a lot of entries offline | `slapadd`, appends, needs slapd stopped | an import task inside the running server, and it **replaces** the backend rather than appending |

Read `subschemaSubentry` from the RootDSE rather than assuming either name.

Two things both servers agree on, which is worth knowing:

- They return a DN with an embedded comma as `cn=Liddell\2C Alice`, using the
  hex-pair escape rather than `\,`. `internal/dn` treats the two forms as equal.
- They base64 a DN line whenever it is not ASCII, so a client that assumes
  `dn:` and never `dn::` will silently lose entries.

## Layout

```
test/compose/
├── docker-compose.yml
├── certs/              generated, gitignored
├── bulk/               generated filler, gitignored, empty unless asked for
├── openldap/           Dockerfile, slapd.conf, alder.schema, entrypoint.sh
├── ds389/              backend.ldif, alder-schema.ldif, bulk-backend.ldif
├── scripts/            certgen.sh, seed.sh, bulk.sh
└── seed/               the LDIF, and gen/ that writes most of it
```

One image, `alder/harness-openldap`, plays four roles: it issues the
certificates, it runs slapd, it seeds both servers, and in bulk mode it drives
389 DS's import. That is why `openssl` and `ldap-utils` are installed in it.

## Notes on the pins

389 DS is pinned by digest. The project publishes only `latest` and a rolling
`c9s` tag, neither of which is reproducible. Bump the digest deliberately, in
its own commit, and re-run the conformance suite.

OpenLDAP is built from `debian:bookworm-slim` rather than a published LDAP
image. Every third-party OpenLDAP image has changed hands, licence or tag
scheme at least once, and the harness has to still build in five years.
